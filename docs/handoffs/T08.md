Inventory entrypoints:

```gdscript
try_add(item_id: StringName, quantity: int, source_id: StringName) -> ActionResult
try_equip(stack_id: StringName) -> ActionResult
try_unequip(slot: StringName) -> ActionResult
try_consume(stack_id: StringName) -> ActionResult
claim_pending(delivery_id: StringName) -> ActionResult
preview_add(item_id: StringName, quantity: int, candidate: Dictionary = {}) -> ActionResult
find_stack(stack_id: StringName, candidate: Dictionary = {}) -> Dictionary
view() -> Dictionary
```

`try_add` is all-or-nothing and uses `inventory/add/<source_id>` for repeat protection. Equipment uses a fresh runtime sequence whose candidate ID is checked against saved receipts, so A-B-A and loading/reconstructing a service cannot accidentally replay an old equip. Attack/heal action lock and travel refuse equip/unequip. Only shield/armor can be unequipped; equip a replacement weapon before selling the old one. `equipment_changed` fires after committed ownership so existing FirstPersonGear and combat readers refresh.

`preview_add` returns item_id, requested, fits, remaining, capacity and key_item. Normal slots fill existing matching stacks before new allocations. `find_stack` and `view` return detached data. `view` includes slots_used, slots_max, stacks, equipment, key_items and pending_delivery.

Stages for use **inside another owner's transaction**:

```gdscript
stage_add(candidate, item_id, quantity, source_id = &"", allow_partial = false) -> ActionResult
stage_reward(candidate, item_id, quantity, delivery_id) -> ActionResult
sale_check(candidate, stack_id, quantity) -> ActionResult
stage_remove(candidate, stack_id, quantity) -> ActionResult
stage_remove_key(candidate, item_id, quantity) -> ActionResult
```

Return or combine the stage's ActionResult.events in the parent transaction. A failed stage must abort that whole transaction. `stage_reward` grants fitting quantities and places overflow under the stable delivery ID in pending_delivery; its added/pending payload and feedback event distinguish outcomes. The owner stages currency and story changes in the same candidate. `reward/<delivery_id>` is a permanent evidence marker that prevents reissuing that item delivery even under a different outer transaction. Claiming is all-or-nothing against current capacity, deletes the pending record, and uses the stable `inventory/claim/<delivery_id>` receipt for repeat calls.

`sale_check` independently rejects removal of the final melee weapon, equipped stacks, invalid quantities and protected items. `stage_remove` reuses that protection and removes normal stacks atomically for selling or completed consumption. `stage_remove_key` is explicitly for quest hand-ins and leaves evidence untouched. There is no generic key discard/sale path.

World entrypoints:

```gdscript
get_entity_state(entity_id: StringName) -> Dictionary
read_loot(entity_id: StringName) -> ActionResult
define_loot(entity_id: StringName, items: Dictionary, crowns: int = 0) -> ActionResult
take_loot(entity_id: StringName, item_id: StringName, quantity: int, transaction_id: StringName) -> ActionResult
take_crowns(entity_id: StringName, transaction_id: StringName) -> ActionResult
mark_defeated(entity_id: StringName) -> ActionResult
apply_transaction(changes: Dictionary, transaction_id: StringName) -> ActionResult
```

`read_loot` returns items, crowns, opened and empty. Queries synthesize detached defaults without saving any record. `take_loot` accepts a selected quantity, collects as much as fits, and leaves the remainder; zero fitting quantity fails without state or receipt changes. `take_crowns` ignores slot capacity and empties the currency field once. Use the same transaction ID for a repeated submission and a new ID for a later intentional partial pickup. Empty containers reject new requests. `mark_defeated` accepts only authored hostile spawn IDs, uses `world/defeat/<spawn_id>`, commits defeat and emits entity_defeated afterwards. Defeat itself pays no crowns. Corpse contents derive exactly from EnemyDef.loot_crowns and cannot be collected before defeat.

`apply_transaction` merges patches shaped `{entity_id: {field: value}}` and permits JSON-safe story data. It cannot edit identity, loot quantities or defeat fields, and cannot reset an opened entity. Use dedicated loot/defeat actions. World scenes remain responsible for physical interactions and story access gates.

## Persistent data and registry

The immutable source file is `res://data/loot/containers.json`, an array of `{id: String, label: String, items: Dictionary<String,int>, crowns: int}`. Root exposes validated copies keyed by id through ContentDB.containers. All thirteen authored sources contain their one specified key item and zero crowns; candle sources each carry one candle. `define_loot` registers a unique definition in the service without editing saved state or ContentDB. Production definitions belong in the validated JSON registry; isolated tests can register fixtures in both the content registry and service when required by shared validation.

Saved container record: `{kind: "container", opened: bool, remaining: {item_id: positive_int}, crowns_remaining: nonnegative_int}`. Empty item entries are erased. Saved corpse adds `{kind: "corpse", defeated: bool, disabled: bool, archetype: String}` and has empty ordinary items. Missing records use the immutable definition; saved records preserve remaining quantities across reconstruction. Generic scene records remain dictionaries with their own story fields.

Permanent key/evidence flags:

- `evidence["<item_id>"] = true` when acquired.
- `evidence["pickup/<entity_id>"] = true` for the unique physical key source.
- `evidence["reward/<delivery_id>"] = true` for a staged reward delivery.

Item and pickup-source evidence_acquired events fire only when first set. Quest hand-in never clears these. Three candle sources remain individually identifiable after their carried counts are consumed.
